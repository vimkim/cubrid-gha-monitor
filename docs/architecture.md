# Data and estimates

The server binds to loopback by default and queries GitHub using a keep-alive HTTPS client authenticated with `gh auth token` (falling back to `gh api` subprocesses if needed), sending `If-None-Match` (`ETag`) conditional headers so unchanged `304` responses do not consume rate-limit quota. The browser requests one snapshot and never receives credentials. A dedicated background polling thread keeps the snapshot warm even without active browser clients (default `--interval 300` seconds, configurable 30–3600s, with 10s–60s retry backoff on errors and automatic pause until reset on GitHub 403/429 rate limits). `POST /api/refresh` wakes the background thread immediately (with a 15s cooldown) for manual refreshes. `monitor.github` scans active statuses in parallel, reads exact attempt job pages, and re-checks the run attempt for non-completed runs. The active scan has a 300-run limit per status. The recent completed scan refreshes every 3 minutes (or immediately when an active run finishes) and skips `conclusion=skipped` runs while retaining up to 100 non-skipped completed runs. A completed attempt with all jobs present and terminal reuses its job details when `updated_at` matches; completed attempts failing with transient errors (such as HTTP 502) enter a 30-minute retry cooldown. PR author lookups expire after 24 hours and viewer login caches for 1 hour.

SQLite stores one observation with its original timestamp. On startup with cached history, the server loads it, runs an immediate active-only refresh first so live queue data clears staleness quickly, and follows up with a completed-history refresh. An incomplete active scan or an unavailable completed-run list leaves the stored observation intact. A failed refresh retains the last snapshot with its original observation time and an error. The server and browser suppress forecast windows when observations are incomplete, a refresh fails, or the snapshot exceeds the dynamic staleness threshold (`max(180, 2 * interval + 60)` seconds).

`monitor.model` derives execution from job states rather than workflow status or a queued job's timestamp. It excludes skipped and cancelled jobs from timing samples. It groups shard numbers within a suite and keeps build modes separate. Historical samples must be successful, valid, within 14 days, and come from at least three distinct attempts. Windows span the smallest and largest available sample, not a confidence interval. Running jobs use only samples longer than their elapsed time. If none remain, the result is unknown.

The pool model orders observed waiting jobs by creation time and job ID. It simulates configured slots with historical minimum and maximum durations. It stops when active coverage is incomplete, a pool or status is unknown, a duration is missing, a running job overruns its history, or a job has waited more than five minutes despite apparently idle configured slots. Configured capacities are assumptions and do not measure healthy runners. Other repositories, unavailable runners, scheduling policy, and jobs that have not yet materialized can invalidate the model.

The whole-CI scenario requires a completed plan, materialized suite jobs, usable waiting-job estimates, and at least three successful completed attempts with the same multiset of job names and pools. It combines the remaining total durations of those matching attempts with the modeled finish of all known unfinished jobs. Each whole-CI bound is at least the corresponding known-work bound. The model clock is read after collection completes. The scenario assumes the current attempt follows that same shape. A missing shape, incomplete scan, unknown state, or overrun yields unknown. The estimate is not a guarantee that later jobs will match the historical shape.

The frontend filters a complete local snapshot. PR authors come from the PR API, not the person who triggered a workflow. For comment-triggered runs, the workflow `head_sha` is not displayed as the tested engine revision.
